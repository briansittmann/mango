## Context

See proposal.md → Why. What exists today, and shapes the approach:

- **The channel is the identity** (`0020`): `canales (usuario_id, tipo, identificador_externo)`, unique per `(tipo, identificador)` and per `(usuario_id, tipo)`, RLS on and no policies; `findUserIdByPhone` resolves the sender there, with the admin client. `usuarios.telefono` is nullable, unique, E.164, and today only the typed number of the closing step.
- **The closing step** (`add-web-onboarding` D11 as `remove-whatsapp-invitations` leaves it): a phone field, "Vincular" stores `telefono` + `whatsapp_solicitado_en` and finishes; `lib/whatsapp/link-request.ts` is a stub. `normalizePhone` (`lib/data/countries.ts`) prefixes the country's calling code and keeps the trunk zero (debt).
- **The adapter** (`lib/whatsapp/adapter.ts`): unknown number → `processUnknownNumber` → `{ kind: 'none' }`; known → idempotency by `mensaje_id_externo`, channel state, logic, confirmation. The payload gives `phone` as `+` + Meta's `wa_id` digits.
- **Reads the web can do**: its own `usuarios` row (select + update, no column list). Nothing in `canales`.
- **The account sheet** (`add-web-onboarding` D16): basics over `SheetShell`, "Guardar" submits a form; account deletion added after.
- **Motion** comes from `motion-skills/` and `globals.css` tokens (`--ease-out`, `--ease-bounce`, `onboarding-fade-in`, `animate-segment-pop`), never approximated. The onboarding is the *rare / first-time* tier of `AUDIT.md` §1, where delight is allowed.
- **Deployment**: Vercel + Supabase, migrations through the MCP with Brian's confirmation, test number of Meta (five recipients, loaded by hand). The decision of 2026-10-03 (ARCHITECTURE §4) fixes the mechanism: the person writes first, from a `wa.me` link with a code.

## Goals / Non-Goals

**Goals:**
- One mechanism that works unchanged with the test number and an owned number: only `WHATSAPP_PHONE_NUMBER` differs.
- The chat is linked by the identifier Meta sends, never by what the person typed.
- Every state the person can be in has a screen: no code, waiting, linked, and the three refusals.
- The web keeps reading nothing from `canales` except its own identifier.
- No new endless animation; the closing step earns its delight with one entrance.

**Non-Goals:**
- Unlinking or changing the linked number from the web (the state *vinculado* has no action; `cuenta-ya-vinculada` is the refusal). Debt.
- Rate limiting of the bot (block 10). The unknown-number memory is its seed, not its implementation.
- Telegram linking (block 11) — the SQL and the state function take `p_tipo` so it can reuse them, nothing more.
- Resolving Meta's Argentine `wa_id` without the 9 (payload TODO): linking stores whatever arrives, so matching never depends on it.
- Removing the phone field once the owned number exists (block 10's last item).

## Decisions

**D1 — The code lives on `usuarios`, generated by the web as the user.** `usuarios.codigo_vinculacion text unique` with a check on `^[A-HJ-NP-Z2-9]{6}$` (32 symbols, no `0/O/1/I`: 2^30 codes, read aloud without ambiguity). `requestWhatsAppLink()` in `ProfileMutations` reads the row; if the code is live (`whatsapp_solicitado_en >= now − 7 d`) it returns it; otherwise it writes a new code and `whatsapp_solicitado_en = now()` through the existing own-row update (RLS `usuarios_update_propio`), retrying up to three times on a unique violation. *Alternative*: a `security definer` SQL function — rejected: the own-row update already exists, and a TS generator with `crypto.getRandomValues` is one function with a unit test. The column has no column-level policy, like the rest of the row (debt already listed in CLAUDE.md).

**D2 — Linking is one SQL function, service role only.** `vincular_canal(p_tipo text, p_codigo text, p_identificador text) returns uuid`, `security invoker`, `set search_path = public`, `revoke execute … from public, anon, authenticated` like `generar_ciclo`. In order: `select … for update` the user by live code, else `raise 'codigo-invalido'`; if a channel `(usuario, p_tipo)` exists → `'cuenta-ya-vinculada'`; if a channel `(p_tipo, p_identificador)` exists → `'numero-en-otra-cuenta'`; `update usuarios set telefono = null where telefono = p_identificador and id <> v_usuario` (only when `p_tipo = 'whatsapp'`); `insert into canales`; `update usuarios set telefono = p_identificador, codigo_vinculacion = null`. One transaction, so a retried webhook cannot link twice (the second call finds no code → `codigo-invalido`, and the adapter already sees the number as known by then anyway). *Alternative*: three statements from TS — rejected: the "clear the other account's typed phone" step and the unique on `telefono` need to be atomic, or a crash in between leaves a code consumed without a channel.

**D3 — The web reads its state through `canal_vinculado(p_tipo) returns text`**, `security definer`, `set search_path = public`, `stable`, body `select identificador_externo from canales where usuario_id = usuario_actual_id() and tipo = p_tipo`, granted to `authenticated`. `canales` keeps RLS without policies, so `pregunta_pendiente` and `ultima_carga_id` stay unreadable (spec `messaging-channels`). *Alternative*: a select policy on `canales` — rejected: it would expose those two columns, which the spec forbids; a view would need its own grants and `security_invoker` juggling.

**D4 — Unknown numbers are remembered in `contactos_desconocidos`** `(tipo, identificador_externo) primary key, primer_mensaje_en, ultimo_mensaje_en, mensajes integer, respondido_en`, RLS on, no policies. One function `registrar_contacto_desconocido(p_tipo, p_identificador) returns boolean`, service role only: upsert (`mensajes + 1`, `ultimo_mensaje_en = now()`), and returns `true` exactly when it set `respondido_en` in this call (it was null). The adapter replies only on `true`, so two simultaneous retries of a stranger's first message cannot both answer. The cron deletes rows with `ultimo_mensaje_en < now() − 90 d` next to `purgeOldMessages`. *Alternative*: a column on `canales` — no, there is no channel; an in-memory set — Vercel keeps nothing between calls.

**D5 — The adapter resolves `vincular` before anything else.** `parseLinkMessage(text)` (`lib/whatsapp/link.ts`): `/^\s*vincular\s+([a-z0-9]{6})\s*$/i`, code uppercased, null otherwise. Order in `handleMessage`: (1) `findUserIdByPhone`; (2) if the text is a linking message: unknown → `linkChannel('whatsapp', code, phone)` (`lib/data/channels.ts`, `rpc('vincular_canal')`) → on success read the account's `idioma` and reply `bot.vinculado`; on `codigo-invalido` / `numero-en-otra-cuenta` / `cuenta-ya-vinculada` reply the matching bilingual text; known → reply `bot.yaVinculado` in the account's language; return in all cases, writing nothing else; (3) unknown and not a linking message: a button press is ignored; otherwise `registrarContactoDesconocido` → `processUnknownNumber({ channel, externalId, text, answered })` returns `bot.desconocido` with `SITE_URL` when `answered` is false, `none` otherwise; (4) the known flow as today. `messageAlreadyProcessed` is not consulted for linking or unknown messages (no transaction is written); a retry of "vincular" after the link lands in the known branch and gets `yaVinculado`, which is harmless. Unknown-number replies are one message with the Spanish line, a blank line and the English line: the account's language is unknown.

**D6 — The number people write to is `WHATSAPP_PHONE_NUMBER`** (digits only, e.g. `15551234567`), distinct from `WHATSAPP_PHONE_NUMBER_ID`, read on the server by `app/onboarding/page.tsx` and `app/dashboard/page.tsx` and passed down as data: `OnboardingData.whatsapp` and `DashboardData.user.whatsapp`, both `{ number: string | null; code: string | null; linked: string | null }`. `lib/whatsapp/link.ts` is pure (no `process.env`): `linkMessage(code)` → `vincular ABC123`, `whatsAppLink(number, code)` → `https://wa.me/${number}?text=${encodeURIComponent(linkMessage(code))}`, `parseLinkMessage`. Without the variable `number` is null and the screens show the manual line; nothing throws. *Alternative*: `NEXT_PUBLIC_…` — rejected: the number is public anyway, but the project keeps every env read on the server.

**D7 — Step 7 flow in the template.** The code is requested when the person leaves step 6 ("Continuar" runs `setSavingsTarget` then `requestWhatsAppLink`, then `go(7)`), so the step mounts with it; on a resume at `?paso=7` the template requests it in an effect and the person's bubble shows the message with a shimmer-free placeholder (`vincular ······`) until it arrives. Phases: `idle` → `waiting` (after the link is activated) → `linked` (when `data.whatsapp.linked` is non-null). The primary slot holds an `<a>` styled as the primary (`target="_blank" rel="noopener"`, the real `wa.me` href, so iOS opens the app on a user gesture) in `idle`; in `waiting` and `linked`, the button "Ir a mi mes" (`finish`). "Seguir sin WhatsApp" stays in `idle` and `waiting`. Re-reading: `onboarding-template` listens to `visibilitychange`/`focus` while in `waiting` and calls `actions.refresh()` (new on `OnboardingActions`: Supabase → `router.refresh()`; demo → re-derives from the sandbox state, flipping to linked when `?e2eVinculado=1`). Without `number`, phase starts at `waiting` and the primary is "Ir a mi mes".

**D8 — The phone field is a molecule, `components/molecules/phone-field.tsx`,** used by the closing step (under a collapsed "Dejar mi número", the `Collapsible` atom, 200 ms `--ease-drawer`) and by the account sheet. A native `<select>` whose options read `🇦🇷 +54` (the flag from the ISO code with regional-indicator code points, no assets) with the country name as `aria-label`, and a `type="tel"` input for the local number; the account's country preselected. Conversion in `lib/data/phone.ts`: `toE164(local, countryCode)` with `parsePhoneNumberFromString` from `libphonenumber-js/min`, `isValid()` required; for `AR`, a number without the mobile `9` gets it (`+54 9 …`): every WhatsApp number is a mobile, and it is how Meta reports Argentine `wa_id`s. `normalizePhone` and its tests are deleted; `countries.ts` keeps `callingCode` for the select. `requestWhatsApp(phone)` keeps its name, writes only `telefono`, and the server action validates with `toE164` against the chosen country (sent with the number, not the account's). Linked numbers are displayed with `formatInternational()`.

**D9 — The account sheet's "WhatsApp" section** sits under the cycle-day line, above "Eliminar cuenta": a state row (icon, title, line) and the phone field. "Vincular WhatsApp" is an `<a>` (same molecule as the onboarding: `components/molecules/whatsapp-link.tsx` renders the action, the code chip and the manual line) whose `onClick` first awaits `requestWhatsAppLink` if the code is not in `user.whatsapp.code` — the page loaded it, so normally the href is ready; when it is not (no live code), the molecule renders a button that requests the code, then swaps to the anchor, so the gesture that opens the app is always the person's. The phone saves with the form's "Guardar" (`requestWhatsApp` after `updateBasics`, only when the number changed). While the sheet is open in `waiting`, the template calls `router.refresh()` on focus. On `/demo` the section renders *sin vincular* with the action disabled (`Controls without a handler are disabled`).

**D10 — Copy.** Web (`onboarding.whatsapp.*`, `cuenta.whatsapp.*`, Spanish in `tú`): `titulo`, `explicacion`, `vincular` ("Vincular WhatsApp"), `irAMiMes`, `seguirSin`, `codigo` ("Tu código"), `sinNumero` ("Envía *vincular {codigo}* a Mango por WhatsApp"), `estadoSinVincular`, `estadoEsperando` ("Esperando tu mensaje"), `estadoEsperandoLinea` ("Cuando llegue, el chat te responde «Listo»."), `estadoVinculado`, `dejarNumero`, `guardarNumero`, `paraQue` (the test-number line), `pais`, `numeroLocal`, `numeroInvalido`, `numeroEnOtraCuenta`, preview bubbles `previewMango` ("✅ Listo, este chat ya está vinculado a tu cuenta."). Bot (`bot.*`, voseo): `vinculado` ("✅ Listo, este chat ya está vinculado a tu cuenta."), `yaVinculado` ("📌 Este chat ya está vinculado a tu cuenta."), `codigoInvalido`, `numeroEnOtraCuenta`, `cuentaYaVinculada`, `desconocido` ("👋 Hola. Mango se usa desde la web: creá tu cuenta en {url} y vinculá WhatsApp desde tu cuenta."); the four replies to an unknown number carry both languages in one string per catalog, joined in the adapter (`es` line + blank + `en` line).

**D11 — Motion of the closing step** (values from `motion-skills/recipies.md` → *Stagger a group entrance* and `globals.css`): the title with the layer; the two bubbles with `onboarding-fade-in` (300 ms `--ease-out`, `translateY(8px)`, `both`), the person's at 150 ms, Mango's at 550 ms (a 400 ms gap reads as a reply, still within the 700 ms budget of the welcome's tier); the state row changes by cross-fade of its text (`transition: opacity 200ms ease`) and the "Vinculado" check uses `animate-segment-pop` (600 ms `--ease-bounce`, the existing token); the code chip is static; nothing loops in `waiting` (a static "Esperando tu mensaje" with the code: a pulsing dot would be an endless animation under *Nothing endless*). Reduced motion: `motion-reduce:animate-none` on bubbles and check, transitions off. The anchor keeps the primary's `onboarding-button` press (scale 0.97, 160 ms `--ease-out`). Never-ship list respected: no `transition: all`, no `ease-in`, nothing over 300 ms except the two repo keyframes.

**D12 — Order and rollback.** `0031` is additive (a nullable column, two functions, one table, one function for the table) and the running code ignores it, so it is applied first, then the code deploys, then `WHATSAPP_PHONE_NUMBER` is set in Vercel (the screens work without it). Rollback: redeploy the previous commit; the column, functions and table can stay or be dropped by hand (`drop function vincular_canal, canal_vinculado, registrar_contacto_desconocido; drop table contactos_desconocidos; alter table usuarios drop column codigo_vinculacion`).

## Risks / Trade-offs

- [Meta's `wa_id` for an Argentine number without the 9 (payload TODO)] → Linking stores the `wa_id` as sent, and later messages come with the same `wa_id`, so the bot matches regardless; only `usuarios.telefono` may differ from what the person typed. Noted, unchanged.
- [The person taps "Vincular WhatsApp" and never sends] → The code stays live 7 days; the state says "Esperando tu mensaje" and the action is offered again; after expiry a fresh code is made on the next tap. Nothing is sent, nothing costs.
- [A code typed by hand to a stranger's phone] → The code links *that* phone to the account: the code is a bearer secret for 7 days. It is 30 bits, shown only on the owner's screens, and the action is the owner's; the chat reply names nothing about the account. Acceptable for a linking step; the risk is listed in CLAUDE.md.
- [Two accounts, same person, same number] → `numero-en-otra-cuenta`: the second account cannot take the number until the first is deleted (account deletion cascades `canales`). No unlink UI yet (non-goal).
- [Unknown numbers still cost one reply each] → One per number per 90 days, atomically. The rate limiting of block 10 bounds the rest.
- [`libphonenumber-js` adds ~65 KB gzipped] → The `/min` build, imported only by `lib/data/phone.ts`, which only the phone field (lazy, under a collapsed line on the onboarding) and the server actions load; the dashboard without the sheet open does not pay it unless the chunk is shared — check the bundle in the apply phase.
- [`router.refresh()` on every focus while waiting] → One server render per tab return, only in `waiting`; stops at `linked`.
- [The `onboarding` delta is written over an unarchived delta] → Same situation `remove-whatsapp-invitations` is in; this change archives after both, in order, and its MODIFIED blocks contain the full requirement text.
