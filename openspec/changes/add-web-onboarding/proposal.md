## Why

Block 9 of `ROADMAP.md` (*Dos onboardings, una cuenta*) and `ARCHITECTURE.md` §4 (*Onboarding web (registro abierto)*). Since `open-web-signup` anyone can create an account with a code by mail, and the trigger of `0025` gives them a `usuarios` row with placeholder values: the e-mail's local part as a name, `EUR`, the browser's timezone, cycle day 1, no country. They then land on an empty `/dashboard` where the free margin reads zero and nothing explains what Mango does with a budget. The eight steps of §4 exist only as text. This change builds the web onboarding — the one that starts after the first login, when the row already exists and nothing has been loaded — so that a new account leaves it with its name, country, currency, cycle, categories, fixed income and expenses, budgets and a savings target, and the dashboard says something from the first visit. It also adds the Argentine peso and a reading format for its large figures, because the first people invited after Brian are in Argentina and `350.000` on every row does not fit a phone.

## What Changes

- **A new route, `/onboarding`**, behind the session, with seven steps in this order: welcome (no "you loaded your first expense"), basics (name, country → currency and timezone, cycle start day), categories, income and fixed expenses, budgets with the free margin moving live, savings target, and a closing screen that stores a WhatsApp number plus an invitation code while `WHATSAPP_REQUIRE_INVITE` is on, or lets the person continue without WhatsApp. Spatial continuity between steps, one direction of travel, back always possible, a discreet progress line instead of "step 3 of 7".
- **Resumable and enforced.** `usuarios.onboarding_paso` remembers the pending step; `/onboarding` opens on it. `/dashboard` redirects to `/onboarding` while `onboarding_completo` is false, and `/onboarding` redirects to `/dashboard` once it is true. Brian's row is already complete and is never redirected.
- **The data it writes is the dashboard's data.** Categories, definitions and budgets go through the existing contracts and server actions (`CategoryMutations`, `RecurringMutations`, `0017`/`0024` functions, budgets as rows of the cycle in progress). The only new write path is one `security invoker` function, `insertar_cargos_pendientes`, that gives each definition created in the onboarding its pending charge of the cycle in progress, exactly the row the cron would have inserted, so the free margin shown in step 5 is the one `/dashboard` shows right after. A new `ProfileMutations` contract covers the `usuarios` fields the onboarding sets (name, country, currency, timezone, cycle day, amount format, savings target, step, completion, WhatsApp request). No Supabase code reaches the browser bundle.
- **Theme control on every onboarding screen**: a floating glass pill top-right with light / dark / system, system selected when the browser holds no choice. Landing and login are always dark, so this is the first place the theme is seen and chosen.
- **`ARS` and the amount format.** Argentina maps to `ARS` and `America/Argentina/Buenos_Aires`. Only an account whose country is Argentina sees a two-way toggle, *abreviado* (`$ 350k`, `$ 1,5M`) or *completo* (`$ 350.000`, `$ 1.500.000`), chosen in step 2 when the currency appears and editable afterwards from the account menu. The preference is `usuarios.formato_montos` (migration `0029`) and is honoured by every amount the web paints (`Money`, `AnimatedAmount`, `CountUp`, `AmountField`'s symbol, the three sheets) and by the bot's replies (`formatBotAmount`). Inputs always take the full number; the abbreviation is read-only. The exact rules of the abbreviated form (thresholds, decimals, rounding, negatives, symbol position) are design D12 and get unit tests in `npm run test:unit`.
- **Country and currency stay editable** after the onboarding: a "Cuenta" row in the account menu opens a sheet with the same basics form (name, country, currency, the format toggle for Argentina). The cycle day is not editable there (see *Interaction with the technical debt*).
- **An in-memory mount at `/demo/onboarding`**, unlinked and `noindex`, so Playwright covers every step, the live margin, the theme control and reduced motion without a database, the way every other UI spec runs on `/demo`.
- **Migration `0029_onboarding_web.sql`**: `usuarios.onboarding_paso`, `usuarios.formato_montos`, `usuarios.codigo_invitacion`, `usuarios.whatsapp_solicitado_en`, and `insertar_cargos_pendientes`. Existing rows take the defaults; nothing touches Brian's data.
- **Closing-screen stub.** The screen stores the number (`usuarios.telefono`) and the code; `lib/whatsapp/link-request.ts` is a documented stub that sends nothing, because the first message is initiated by Mango and needs a Meta template (block 10). The copy says the number was saved and that Mango will write, not that a message was sent.
- Tests: unit tests for the amount format and the country table; Playwright specs over `/demo/onboarding` and for the redirects; a manual pass against the real project with a `+` alias, including a run of the cron route to prove it inserts nothing twice.
- Documentation: `ARCHITECTURE.md` §2 (currencies, `ARS`), §4 (the onboarding as built), §8 (new columns); `ROADMAP.md` block 9; `CLAUDE.md` state and debt.

### Interaction with the technical debt

- **"Todos en EUR hasta el onboarding"** closes. Step 2 asks the country and sets `moneda_default` and `timezone` before any row is written: the onboarding runs before the dashboard, and the trigger's `EUR` is only ever a placeholder nobody sees. Brian's row is untouched.
- **"Monedas mezcladas"** stays, and becomes reachable from the UI: the "Cuenta" sheet lets a person change their currency after they have rows, and `resumenMensual` keeps summing `monto` without looking at `moneda`. The sheet says so in one line when the account has movements ("los movimientos ya cargados mantienen su moneda y se suman sin convertir"). Converting is still out of scope; the debt entry gains the sentence "now reachable from the account sheet".
- **"`presupuestos.periodo` si cambia `dia_inicio_ciclo`"** is why the cycle day is editable only while the account holds no category, definition, budget or movement: in step 2 of a fresh account there is nothing keyed to the cycle, so a change re-keys nothing (design D6). The "Cuenta" sheet shows the day read-only. The debt entry stays as it is.

### Not in this change

The WhatsApp onboarding by chat and the one-time link that opens a session; sending the linking message (block 10: Meta template, `invitaciones` validation, rate limiting); the "WhatsApp" section in settings; Telegram; instalment plans (`repeticiones`) from the onboarding (added later from the dashboard's entry sheet); a reminder control in the onboarding; editing the cycle day after data exists; converting amounts between currencies; `usuarios.idioma` following the language selector; the bot's handling of `onboarding_completo = false` (the TODO in `lib/bot/logic.ts` stays); photo upload; Google login.

### Risks named up front

- **A write path for charges outside the cron.** `insertar_cargos_pendientes` runs as the user and inserts only pending rows of the cycle in progress or later for the user's own active definitions, `on conflict do nothing`, counting a repetition only when the cycle was already generated (the rule of `sumar_repeticion`). The cron's `generar_ciclo` skips existing rows and counts them once, so the two never double-insert or double-count; the manual pass runs the cron route after an onboarding to prove it.
- **Live free margin and stored figures disagreeing.** Step 5 computes the margin in the browser from the typed budgets and the definitions' expected amounts; the dashboard computes it from rows. They agree because the pending rows exist at expected amounts before step 5 is shown, and because both call `getFreeMargin`. The manual pass compares the two numbers.
- **`narrowSymbol` changes the symbol of non-euro currencies everywhere** (`ARS` → `$`, `USD` → `$` instead of `US$`). Brian is in `EUR`, unchanged; the demo is in `EUR`.
- **The onboarding is the first place where the "no stored theme" case is seen.** Entering it stores `system` when nothing is stored, so the dashboard afterwards follows the OS; a browser that already chose keeps its choice.

## Capabilities

### New Capabilities

- `onboarding`: the web onboarding at `/onboarding` — who is sent there and when, the seven steps and what each one stores, the pending-step resume, the floating theme control, the live free margin, the closing screen's stored request, the in-memory mount at `/demo/onboarding`, and its motion in both motion settings.

### Modified Capabilities

- `web-access`: *The dashboard requires a session* — `/dashboard` redirects to `/onboarding` while the onboarding is not complete, `/onboarding` requires a session and redirects to `/dashboard` once complete, the session refresh covers `/onboarding`; *Account created on first confirmed sign-in* — a new account's first visit lands on the onboarding, not on an empty dashboard, and the row carries step 1 and the complete amount format.
- `dashboard-ui`: *Account avatar and menu* — the menu gains a "Cuenta" row that opens the account sheet (name, country, currency, the format toggle for Argentina, the cycle day read-only), disabled when the page supplies no profile operations.
- `theming`: *Theme selection* — the onboarding's floating control, "system" as its default, stored on entry when the browser holds no choice.
- `localization`: *Locale-aware formatting* — the narrow currency symbol, `ARS` in Spanish laid out as in Argentina (`$ 350.000`), and the abbreviated reading format; new *Amount format preference*.
- `dashboard-data`: *Every dashboard operation persists* — the profile operations, the savings target, the pending charges written for definitions created in the onboarding, the step and completion marks; the data supplied to the dashboard carries the country and the amount format.
- `design-system`: *Translucent materials* — the onboarding's floating theme control and back control join the list of translucent controls.
- `bot-transaction-logging`: *Replies are plain text in the account's language* — amounts in replies follow the account's amount format.
