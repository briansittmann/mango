## Context

See proposal.md → Why. What shapes the approach:

- `/login` is the two-step page of `replace-magic-link-with-email-otp` (open, 24/33). The e-mail step is `app/login/login-form.tsx` with `useActionState` over the server action `requestCode` (`app/login/actions.ts`), which calls `signInWithOtp({ email, options: { shouldCreateUser: false } })`; `login-steps.tsx` reuses `requestCode` for "Reenviar". The code is verified by the route handler `POST /auth/verify-code` (that change's D2 amendment: a server action that sets cookies re-renders `/login`). `lib/auth/otp-status.ts` maps provider errors; "Signups not allowed for otp" is already mapped to `sent`, so an unknown address looks like a known one.
- `usuarios` (live schema): `nombre`, `pais`, `timezone`, `moneda_default` are `NOT NULL` with no default; `email` is unique and nullable; `dia_inicio_ciclo` defaults to 1, `idioma` to `'es'`, `onboarding_completo` to false. `auth_user_id` is unique, `on delete set null`. RLS lets a user select and update only their own row and has **no insert policy** (`0011`): the header of `0011` already expected row creation to happen outside the user's own permissions. No TypeScript reads `pais`.
- The real project has one auth user and one `usuarios` row, linked, e-mail confirmed, `onboarding_completo = true`, no `idioma` in the auth metadata. No trigger exists on `auth.users` or `usuarios`.
- With `shouldCreateUser: true`, Supabase creates the auth user **when the code is requested**, unconfirmed; the first valid code confirms the e-mail (`email_confirmed_at` goes from null to a time). For a new address it sends the *Confirm signup* template, not *Magic Link*. `options.data` becomes the new auth user's `user_metadata` and is ignored for an existing user.
- Supabase e-mail templates are Go templates. `{{ .Data }}` is `user_metadata`; `{{ .Token }}` the code; subjects are templated too (the default reauthentication subject uses `{{ .Token }}`).
- The locale is the `locale` cookie (`i18n/request.ts`), set by the server action `changeLanguage` (`app/actions/language.ts`), which `/demo` and `/dashboard` both pass to the account menu.
- `resumenMensual` already handles a user with no categories and `ciclo_generado_hasta` null (the projection counts from the cycle before; the cron generates the cycle in progress on its next run, with nothing to insert).

## Goals / Non-Goals

**Goals:**
- A stranger goes from Home to a signed-in, empty dashboard with one form and one code, and never sees "cuenta sin vincular".
- The `usuarios` row exists for every confirmed auth user, whatever path confirmed it (the code today, Google in block 13), without opening an insert permission to users and without the service-role key in the web path.
- Brian's row, auth user and data untouched by the migration, the triggers and the deploy.
- The code mail branded and in the account's language, with no new endpoint on the critical path of signing in.

**Non-Goals:**
- Keeping `usuarios.idioma` in step with the language switch. It is set once at creation; the switch only moves the auth metadata that the mail reads. The bot's reply language (which reads `usuarios.idioma`) is a WhatsApp concern and web accounts have no channel yet.
- Linking a new auth user to an existing `usuarios` row by e-mail (a bot-created user who later registers on the web). That is the "link WhatsApp to a web account" flow of block 9/10; here the trigger simply skips the conflict.
- Deleting unconfirmed auth users.

## Decisions

**D1. A trigger on `auth.users`, fired on confirmation, creates the row.** Two triggers call one `security definer` function: `after insert` when the new row already has `email_confirmed_at` (a user created confirmed: admin, OAuth later), and `after update of email_confirmed_at` when it goes from null to not null (a new address typing its first code). The insert runs in the same transaction that confirms the e-mail, so by the time `/auth/verify-code` answers `ok`, the row exists.
- Why a trigger and not the server in `/auth/verify-code`: the route would need the service-role key (no insert policy) or a new insert policy for `authenticated`; it would cover only this path, so `/auth/confirm` and the Google callback of block 13 would each need the same call; and a failure between "session set" and "row inserted" leaves exactly the unlinked state this change removes. The database is the one place every sign-up path goes through.
- Why on confirmation and not `after insert` (Supabase's usual example): `shouldCreateUser: true` inserts the auth user when the code is *requested*. A row on insert would give a `usuarios` row to every address anyone types, confirmed or not; on confirmation, only a person who proved they read that mailbox gets one.
- Why not "create it lazily on `/dashboard`": a GET that writes, run on every visit until it succeeds, and it still needs a definer function or the service key. Rejected.
- Brian: his auth user is already confirmed, so neither the insert nor the null→not-null update fires for him. Nothing in the migration touches existing rows except the `pais` constraint (D2).

**D2. Defaults of the new row, and `pais` nullable.** `auth_user_id` = the auth user; `email` = its address; `nombre` = the part before `@` (the avatar's initial works from day one, and block 9 asks the real name); `idioma` = `user_metadata.idioma` if it is `es` or `en`, else `es`; `timezone` = `user_metadata.timezone` if it is in `pg_timezone_names`, else `UTC`; `moneda_default` = `EUR` (Brian's currency and the demo's; the country → currency question is block 9's); `dia_inicio_ciclo` 1 and `onboarding_completo` false from the column defaults; `pais` null. The migration drops `NOT NULL` from `pais` instead of inventing a value: nothing reads it, and a made-up country would look like data. The alternative of guessing the country and currency from the timezone was rejected: a table of zones to countries for a value that the onboarding asks anyway.

**D3. The trigger never breaks a sign-in.** `insert … on conflict do nothing` (no conflict target, so it covers both `auth_user_id` and `email` uniqueness): an auth user with a row, or an address held by another row, gets nothing. The body sits in `begin … exception when others then raise warning …; end`, so any other failure (a constraint, a bug) logs a warning in Postgres and lets GoTrue finish: the person signs in and sees *Unlinked account*, which is recoverable, instead of Supabase's opaque "Database error saving new user", which is not. The function is `security definer`, owned by `postgres`, `set search_path = ''` with every name qualified, and `execute` revoked from `public`, `anon` and `authenticated` (triggers do not need it; the advisors flag it otherwise). Metadata is user-controlled, so both values are validated in SQL and never cast blindly.

**D4. First landing: `/dashboard`, empty. No onboarding placeholder.** "Ir a mi mes" already leads to `/dashboard`, and an empty dashboard is usable: "Añadir categoría", income, expenses. A placeholder route would be a screen where the person can do nothing, that block 9 replaces anyway. Block 9 adds the redirect on `onboarding_completo = false`; Brian's row is already `true`, so that redirect will not catch him. The success copy ("Listo, entraste", "Ir a mi mes") stays as is for new and returning people.

**D5. The code request moves to a route handler, `POST /auth/request-code`.** Body `{ email, idioma, timezone }`, answer `{ status: 'sent' | 'rate_limited' | 'error', email? }` with the same `sendStatus` mapping, never throws. It calls `signInWithOtp({ email, options: { shouldCreateUser: true, data: { idioma, timezone } } })`. The client reads `idioma` from `useLocale()` and `timezone` from `Intl.DateTimeFormat().resolvedOptions().timeZone`; the route keeps `idioma` only if it is `es`/`en` and `timezone` only if it is a short string (≤ 64 characters, the trigger checks it is real), and drops them otherwise. `login-form.tsx` keeps `useActionState`, with a client function that posts to the route in place of the server action; `login-steps.tsx` uses the same function for "Reenviar".
- Why: the spec for "new address → code step" must run without a database or a mail. Playwright can stub a `fetch` to a route (`page.route('**/auth/request-code')`, as `login-code.spec.js` already does for `/auth/verify-code`); it cannot reasonably fake a server action's response, whose format is internal to Next.js. Calling the real provider from a test would create real auth users and send real mails against the 30-per-hour cap. The switch also matches the other half of the page: request and verify are both route handlers.
- What it does not change: `replace-magic-link-with-email-otp`'s D2 contract (statuses, mapping, the unknown-address rule). Only the transport moves. Its tasks are done; this change owns the edit.

**D6. Language of the mail: metadata in the template, not a Send Email Hook.** The template branches on `user_metadata.idioma`. A Send Email Hook (Supabase calls an endpoint of ours, which renders and sends through Resend's API) would let the language come from `usuarios.idioma` and the mail be built in React, but it puts a new endpoint, a Resend API key in Vercel and a signed webhook on the only path by which anyone signs in: if that endpoint fails, nobody gets a code. The metadata route keeps Supabase's SMTP, rate limits and retries as they are and adds no secret. Revisit if the mail outgrows a template (several mails, more languages).
- Where the metadata comes from: at sign-up, `options.data` (D5). Afterwards, `changeLanguage` writes it when there is a session (D7). Accounts from before (Brian) have none and get Spanish.
- Robust branch: a missing key or a nil `.Data` must not make the template fail (a failed render means no mail, so no sign-in). The template computes the branch once with guarded `if`s and never compares a possibly missing value:
  `{{ $en := false }}{{ if .Data }}{{ if .Data.idioma }}{{ if eq .Data.idioma "en" }}{{ $en = true }}{{ end }}{{ end }}{{ end }}`
  and then `{{ if $en }}…English…{{ else }}…Spanish…{{ end }}` in the body. The subject uses the same guarded form inline.

**D7. Switching language while signed in updates the metadata.** `changeLanguage` keeps setting the cookie and, when `supabaseServer().auth.getClaims()` finds a session, calls `auth.updateUser({ data: { idioma } })`. Errors are swallowed and logged: the language of the page must switch even if the auth call fails. Without a session (Home, `/login`, `/demo` signed out) it touches nothing on the server. Why not also at every successful verify (the language of the page where the code was typed): it would make the mail language drift with whatever page a person happens to sign in from; the account menu is the explicit choice.

**D8. The template.** One file, `supabase/templates/codigo.html`, pasted into both *Magic Link* and *Confirm signup* (a new address's first code uses the second; without it, a new person gets Supabase's default confirmation mail with a link and no code, and cannot sign in). Built for mail clients: a centred table 480 px wide, inline styles, no CSS variables, no `light-dark()`, no SVG. Colours are the light values of the `design-system` tokens written as hex (`--background` #F4F7F4 page, `--card` #FFFFFF card, `--border` #E6E9E6, `--foreground` #171A17, `--muted-foreground` #5F665F, `--muted` #E8EFE8 behind the code, `--brand` #149052 accent); a `<style>` block with `@media (prefers-color-scheme: dark)` swaps in the dark values for clients that honour it (Apple Mail, iOS), and `<meta name="color-scheme" content="light dark">`. Type: Manrope from Google Fonts in a `<link>` (loads in Apple Mail/iOS), stack `Manrope, -apple-system, 'Segoe UI', Helvetica, Arial, sans-serif`; heading 700 as `text-headline-lg`, body 16 px, the code 32 px, 700, `letter-spacing: 6px`, `font-variant-numeric: tabular-nums`, alone on its line inside a `--muted` box, next to "código"/"code" so iOS offers it as autofill. Logo: `public/email/mango-logo.png`, a 2× PNG of `public/mango-logo-light.svg`, referenced by absolute URL `https://www.usemango.dev/email/mango-logo.png` with `alt="Mango"`, width and height set (mail clients block SVG, and a relative URL does not resolve in a mail). Text, per language: the heading ("Tu código para entrar a Mango" / "Your code to sign in to Mango"), the code, "Escríbelo en la página donde lo pediste. Vence en 10 minutos." / "Type it on the page where you asked for it. It expires in 10 minutes.", "Si no lo pediste, ignora este mail." / "If you didn't ask for it, ignore this e-mail." Spanish in `tú`, like `messages/es.json`. Subjects: "Tu código de Mango" / "Your Mango code". The file carries a comment at the top with both subjects and the two panel entries it goes into; `supabase/templates/` is documentation for the panel, not read by the app.

**D9. The e-mail step's hint.** One line under the field, `text-body-sm text-muted-foreground`, from `acceso.primeraVez` ("Si es tu primera vez, creamos tu cuenta con este mail." / "First time here? We'll create your account with this e-mail."). It is the only copy change on `/login`; the heading stays "Entrar a Mango". The Home line is `inicio.descripcion` in `text-body-md text-muted-foreground`, centred, `max-w-sm`, under the two buttons.

**D10. Tests.** `tests/home.spec.js`: the line is visible and names the invitation, in Spanish and (with the `locale=en` cookie) in English; the no-Supabase-request assertion stays. `tests/login-signup.spec.js` (new): the hint on the e-mail step; with `page.route('**/auth/request-code')` fulfilled as `{ status: 'sent', email }`, submitting a made-up new address shows the code step with that address and `/login?email=` in the URL, and the stubbed request body carries the address, `en` (cookie) and `Europe/Madrid` (`test.use({ timezoneId: 'Europe/Madrid' })`); a stubbed `rate_limited` shows "demasiados pedidos" and a stubbed `error` the send error. No test reaches Supabase. `tests/login-code.spec.js` counts POSTs on the code step; it is re-run because "Reenviar" now posts to `/auth/request-code`. The trigger, the templates, the language sync and the empty dashboard are checked by hand against the real project (tasks), with a `+` alias of Brian's own mailbox as the new address, cleaned up afterwards.

## Risks / Trade-offs

- [Open registration without rate limiting: anyone can make Mango mail any address, and the 30 mails per hour of the SMTP are shared by every sign-in and sign-up, so a burst locks everyone out for the rest of the hour] → Supabase's per-address 60 s interval and the hourly cap bound it; the `rate_limited` message tells the person to wait; turning sign-ups off in the panel is the brake (the app keeps answering an unknown address as today). Rate limiting on registration and a CAPTCHA (Supabase Auth supports Turnstile/hCaptcha on `signInWithOtp`) go with block 10. Written into `ARCHITECTURE.md` §10 and §11.
- [Mails to addresses that never asked hurt `usemango.dev`'s sending reputation in Resend] → same brakes; watch bounces and complaints in the Resend dashboard after opening.
- [Resend's plan has its own daily cap] → Brian checks the plan's number and records it next to the 30/h (task); if it is lower than a day of 30/h, it is the real ceiling.
- [Unconfirmed auth users pile up] → they hold no `usuarios` row and no data; a periodic cleanup is noted as technical debt.
- [A template error means no mail at all, so no sign-in] → D6's guarded branch; the template is tested first in *Confirm signup* with a new alias (only new addresses use it), then pasted into *Magic Link* and tested with Brian's address (no metadata → Spanish). The previous template text stays in the tasks of `replace-magic-link-with-email-otp` (0.1) for a quick revert.
- [The trigger swallows a real bug and people land on "cuenta sin vincular"] → the warning is in the Postgres logs; the manual check covers the path end to end; an unlinked auth user can be fixed by hand with one insert.
- [`EUR` for everyone until block 9] → a person in another country sees euros; the onboarding of block 9 asks the country and sets currency and timezone. Named in `CLAUDE.md` technical debt until then.
- [A person registers with an address that a `usuarios` row already holds without an auth user (a future bot user)] → no row is created and they see "cuenta sin vincular"; linking is block 9/10. Today no such row exists.
- [`nombre` is the e-mail's local part ("brian.reba97")] → only the avatar initial uses it before block 9 asks the name.
- [Archive order] → the `web-access` delta modifies *Sign-in by e-mail code*, which only exists once `replace-magic-link-with-email-otp` is archived; archive that one first, like the D8 note of `add-entries-in-projected-cycles`.

## Migration Plan

Order, each step safe on its own:

1. **Migration `0025`** (🤖, through the MCP, with Brian's confirmation), before the code, like every migration here. Safe alone: sign-ups are off and `/login` still sends `shouldCreateUser: false`, so no auth user is created or confirmed; Brian's is already confirmed. Check afterwards that his row and auth user are byte-for-byte as before (query in the tasks).
2. **Templates** (👤 Brian): paste `codigo.html` and the subject into *Confirm signup*, then into *Magic Link*. Safe alone: existing accounts get the new design in Spanish.
3. **Deploy** the app. Safe with sign-ups still off: an unknown address gets "Signups not allowed for otp", mapped to `sent`, the same silent answer as today; existing accounts sign in as before, and their language switch starts writing metadata.
4. **Sign-ups on** (👤 Brian, Auth → Sign In / Providers → *Allow new users to sign up*). From here an unknown address gets an account. Deploy before this step so that the moment registration opens the page already has the hint and sends language and timezone; turning it on first would open registration with the old copy and Spanish-only metadata.
5. **Check by hand** with a new alias (tasks), then clean up that alias's rows.

Rollback: sign-ups off (instant, panel) closes registration without a deploy. The trigger can stay: with sign-ups off it never fires. Reverting the app is only needed if the route itself misbehaves; the old server action and the new route answer the same statuses.
