## Why

The WhatsApp webhook is in production and already knows who is writing, but `lib/bot/logic.ts` answers `{ kind: 'none' }` to everything: a message reaches Mango and nothing happens. Loading an expense from the chat is the one thing the app needs to happen every day (ARCHITECTURE.md §3, *Sin repregunta de categoría*), and since 2026-09-27 the database holds Brian's real data, so the bot can start being used for real. This is the first half of block 5 of `ROADMAP.md`: the bot understands a message and logs the transaction; conversation (undo, corrections, queries, categories by chat, VIP history, onboarding, invitations, rate limiting) is `add-bot-conversation`.

## What Changes

- **Dependencies**: `zod` and `@google/genai` in `package.json`; `GEMINI_API_KEY` read server-side only (already listed in ARCHITECTURE.md §2).
- **Parser** (`lib/bot/parser.ts`): one Gemini call with a prompt built from the user's own categories (names from the database, never hard-coded) and the names of their active recurring expenses, JSON output validated with a Zod schema; one retry when the output is not JSON or fails the schema; two failures → `no_entendido`. The schema covers every action in `lib/bot/parser-cases.json` (`cargar`, `repreguntar`, `no_entendido`, `consultar`, `corregir`, `borrar`, `crear_categoria`) so the whole test set can be evaluated, but only `cargar`, `repreguntar` and `no_entendido` are executed here; the other four reply "I can't do that yet" until `add-bot-conversation`.
- **Logging** (`lib/bot/logic.ts`): `gasto`, `ingreso` and `ahorro` (a withdrawal is a negative amount), `dias_atras` turned into a calendar day in the user's timezone, the user's `moneda_default`, written through the existing `lib/data/supabase/*` creators with the service-role client. The row records `canal` + `mensaje_id_externo`, so the idempotency check that already exists in the adapter discards Meta's retries. A category the parser cannot map goes to **Otros** without asking (§3); a message with an amount and no description at all ("gasté 50") asks for the category in text, listing the user's categories.
- **Pending question across turns**: the adapter owns conversation state, but a Vercel function holds nothing between two webhook calls, so the pending question is persisted per channel (`canales`) with an expiry. The next message from that channel answers it or replaces it; an expired one is dropped. Migration `0023`.
- **Recurring match**: a `gasto` that names one of the user's active recurring expenses ("netflix 13", "luz 120") completes this cycle's pending charge through `completar_cargo_recurrente` instead of inserting a second row (§7, *Filas pendientes*). When the amount differs from the expected one the logic returns the `recurring-discrepancy` reply that `BotReply` already defines; the adapter still only logs it (its follow-up question is `add-bot-conversation`). An `ingreso` never matches a definition: "cobré 2100" and "propina 500" are separate incomes (decision of 2026-09-27).
- **Replies**: a plain-text confirmation (amount, category, date), the category question, the "didn't understand" text and the "not yet" text, all from `messages/es.json` and `messages/en.json` under a `bot` namespace, chosen by `usuarios.idioma` (§2). Text only: no Undo button, no reaction, no `cargas_confirmadas` counter (progressive confirmation is `add-bot-conversation`).
- **Sending**: the adapter's `sendReply` actually posts the text to the WhatsApp Cloud API (`WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`). Not in the block-5 list as its own item, but without it the real test round cannot happen.
- **Parser evaluation**: `npm run test:parser` runs the 15 cases of `parser-cases.json` against real Gemini and prints pass/fail per case. It is not part of `npm run test:unit` because it needs the network and a key.
- **Not in this change** (`add-bot-conversation`): progressive confirmation and Undo, corrections and deletion, queries, category creation by chat, VIP history and the `mensajes` table, 30-day message deletion, onboarding by chat, invitations, rate limiting, the adapter's follow-up question for a recurring discrepancy.

## Capabilities

### New Capabilities
- `bot-message-parsing`: how a chat message becomes a structured action — the prompt's inputs (user's categories and recurring names, language, today), the action schema, JSON validation and retry, the fallback to `no_entendido`, and the evaluation set.
- `bot-transaction-logging`: what the bot does with a parsed action — writing an expense, income or savings movement for the account with the right date, cycle, currency and message origin; mapping categories and the Otros fallback; completing a pending recurring charge; the pending category question and its lifetime; the reply texts and their language; what the not-yet-supported actions answer.

### Modified Capabilities
- `messaging-channels`: a channel can hold one pending question with an expiry (new requirement), and the bot logic receives the pending question together with the message (*The bot logic does not know the channel's mechanics* gains the pending question as an input).
