## Context

See proposal.md → Why. What shapes the approach:

- **The row exists before the onboarding.** `0025` creates `usuarios` at the first confirmed code with `nombre` = e-mail local part, `moneda_default` `EUR`, `timezone` from the browser (else `UTC`), `dia_inicio_ciclo` 1, `onboarding_completo` false, `pais` null. RLS (`0011`) lets the signed-in user select and update their own row, with no column restriction, and has no insert policy. Brian's row is `onboarding_completo = true`, `pais = 'IE'`, cycle day 28.
- **Every dashboard write goes through a contract in `lib/data/` with two implementations** (`lib/demo/*` in memory, `lib/data/supabase/*` behind server actions in `app/dashboard/actions.ts`, each action `revalidatePath` after the write). `CategoryMutations.create(draft, cycle, scope)` calls `crear_categoria` with `p_periodo` = the displayed cycle's first day and sets `desde_ciclo`; `update(id, draft, { cycle, scope: null })` writes the budget row of the cycle in progress through `actualizar_categoria`; `RecurringMutations.create(target, draft)` calls `crear_movimiento_recurrente`, which only links a transaction row that already exists (the entry sheet creates that row first; here none exists) and resolves with nothing. `SavingsMutations` has no target setter; `meta_ahorro_mensual` (`0016`) has no UI anywhere.
- **The cycle in progress shows real rows only.** `resumenMensual` projects charges (`proyectarCiclo`) for cycles *after* the one in progress; the cycle in progress lists stored rows. With `ciclo_generado_hasta` null the cron's next run (05:00 UTC) calls `generar_ciclo` for the cycle in progress and inserts pending rows for every active definition; if the cron already ran for that cycle (marker = cycle), `generar_ciclo` returns 0 for it. `generar_ciclo` and `cerrar_pendientes` have `execute` revoked from `authenticated` (`0021`). `editar_cargo_en_ciclo` (`0024`) writes a definition's slot in a cycle but inserts it **confirmed** when the cycle is the one in progress (`p_periodo <= v_actual`): it is the entry sheet's "this row is real" path. `sumar_repeticion` counts a repetition only when the cycle was already generated; otherwise `generar_ciclo` counts it when it generates (D4 of `add-forward-scoped-edits`).
- **The free margin is one formula.** `getFreeMargin({ income, savings, categories: [{ budget, spent }] })` in `lib/data/budget.ts`: `income − savings − Σ (budget == null ? spent : max(budget, spent))`. In the cycle in progress `spent` includes pending charges at their expected amount and `savings` is the signed sum of the cycle's movements (not the target).
- **Formatting.** `currencyFormatOptions` (`i18n/formats.ts`) is `{ style: 'currency', trailingZeroDisplay: 'stripIfInteger', useGrouping: 'always' }`, used by `Money`, `AnimatedAmount`, `AmountField`, the sheets and `formatBotAmount`. The app locale is plain `es` or `en`. `Intl` with `es` and `ARS` gives `350.000 ARS` (no `$`), with `narrowSymbol` `350.000 $` (symbol after), and with `es-AR` and `narrowSymbol` `$ 350.000` — the Argentine layout. `en` + `narrowSymbol` gives `$350,000`. `CountUp` (`motion/react`) takes a `format` callback; `AnimatedAmount` passes a locale/currency formatter of the number only and paints the symbol beside it.
- **Theme.** `data-theme` on `<html>`: the root layout's inline script forces dark on `/` and `/login`, and elsewhere reads `localStorage.theme` — `null` is treated as dark (`theme !== 'system'`), so a browser with no choice is dark (`theming` → *Theme selection*). `ForceDarkTheme` restores the stored choice on leaving `/login`. The account menu's theme control (`account-menu.tsx`) applies a choice with a view-transition circle (`700ms cubic-bezier(0.32, 0.72, 0, 1)`) and the `segment-track` / `segment-thumb` classes.
- **Motion vocabulary already in the repo.** `app/globals.css` defines `--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`, `--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`, `--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1)` (the three curves of `motion-skills/AUDIT.md` §2 and `animations.md` §5), plus `--ease-spring` and `--ease-bounce` (`linear()` curves), the `header-pop` (700ms `--ease-bounce`) and `header-in` (600ms `--ease-out`) entrances, `segment-pop`, and `.liquid-glass` / `.glass-bar` materials. `gsap` is in the repo (`animated-content.tsx`); `motion` is in the repo (`count-up.tsx`). Sheets open on `ease-spring` 500ms (`sheet-shell.tsx`).
- **`motion-skills/` rules this design must satisfy** (`AUDIT.md`, `animations.md`, `recipies.md`, `Apple-desing.md`, `improveanimations.md`): entering/exiting on `ease-out`, on-screen movement on `ease-in-out`, never `ease-in`; UI under 300 ms, explanatory/first-time moments may run longer; `transform` and `opacity` only; never `scale(0)`; transitions (not keyframes) for anything retargeted; springs for anything live; reduced motion keeps opacity changes and drops movement; `:hover` motion gated on `(hover: hover) and (pointer: fine)`; the onboarding sits in the "rare / first-time" row of the frequency table, where delight is allowed, and nothing decorative goes on what repeats.
- **Tests.** UI specs run on `/demo` (in memory, no network); specs that need an account (`/dashboard`) are manual against the real project. `npm run test:unit` runs `lib/**/*.test.mjs` with Node, importing `.ts` through relative paths.

## Goals / Non-Goals

**Goals:**
- A new account goes from "Ir a mi mes" to a dashboard whose free margin is a real number, in one sitting on a phone, without reading a tutorial: step 5 teaches the envelope model by moving the number.
- Everything the onboarding stores is indistinguishable from what the dashboard would have stored: same functions, same `periodo`, same `desde_ciclo`, same pending charges the cron would have inserted.
- The onboarding is a template with injected contracts, like the dashboard, so it runs in memory for tests and against Supabase for real.
- One formatter for amounts, shared by the web and the bot, with the abbreviated form as a pure function under unit tests.
- Motion that passes the `motion-skills/` review on the first pass: every curve, duration and spring copied from those files or from `globals.css`, and reduced motion handled in the same commit as each animation.

**Non-Goals:**
- Re-running the onboarding later (the "Cuenta" sheet covers what stays editable). Editing the cycle day after data exists.
- A cross-route morph of the free margin into the dashboard's card: the hand-off is a plain navigation (D14 says why).
- Validating the invitation code or sending any WhatsApp message (block 10).
- Localised country names in the catalogs: `Intl.DisplayNames` provides them.
- Changing the no-choice theme default outside the onboarding (`/demo` for a first-time visitor stays dark).

## Decisions

**D1. One route, `/onboarding`, gated both ways, resumed from `usuarios.onboarding_paso`.** `app/onboarding/page.tsx` is a server component: no session → `redirect('/login')`; no `usuarios` row → the same "cuenta sin vincular" screen as `/dashboard`; `onboarding_completo` true → `redirect('/dashboard')`; otherwise it loads what the template needs (D2) and mounts it on `onboarding_paso`. `app/dashboard/page.tsx` adds, after `findCurrentUsuario`, `if (!usuario.onboarding_completo) redirect('/onboarding')`. `proxy.ts` adds `/onboarding/:path*` to its matcher so the session refresh and the unauthenticated redirect cover it. `generateMetadata` sets `robots: { index: false, follow: false }` like `/dashboard`. Every step change — forward and back — writes `onboarding_paso` through `ProfileMutations.setStep` (one small update; optimistic in the UI), so a reload or a return days later opens the pending step; the URL stays `/onboarding` with no query, so the browser's back button leaves the onboarding rather than stepping inside it (the in-page "Volver" is the step control). "Ir a mi mes" on `/login` keeps leading to `/dashboard`, which redirects once; no copy changes on `/login`.
- Why a stored step and not a derivation from the data: steps 3–6 can legitimately be left empty, so "has categories" does not say where the person is.
- Why `/dashboard` redirects and not the proxy: the proxy has no `usuarios` row; the page already reads it.
- Brian: `onboarding_completo = true`, never redirected. Test aliases created before this change (none exist today) would be sent to the onboarding, which is correct.

**D2. A template with injected contracts, mounted twice.** `components/templates/onboarding-template.tsx` (client) renders from `OnboardingData` and `OnboardingActions`, like `DashboardTemplate` renders from `DashboardData` and `DashboardActions`. `OnboardingData` = `{ step, profile: { name, country, currency, timezone, cycleDay, amountFormat, savingsTarget, phone, inviteCode }, cycle: { start, today }, categories: { id, name, color }[], definitions: RecurringDefinition[], budgets: Record<categoryId, number | null>, hasData: boolean, inviteRequired: boolean }`. `OnboardingActions` = `{ profile: ProfileMutations; categories: Pick<CategoryMutations, 'create' | 'update' | 'delete'>; recurring: Pick<RecurringMutations, 'create' | 'update' | 'stop' | 'delete'>; materializeCurrentCycle(): Promise<void>; finish(): Promise<void> }`. Two mounts:
- `app/onboarding/supabase-onboarding.tsx` binds the server actions of `app/onboarding/actions.ts`, each `run(ctx => …)` + `revalidatePath('/onboarding')`, reusing `createSupabaseCategoryMutations` and `createSupabaseRecurringMutations` as they are (the same `DataContext` as `/dashboard`). After a write the page re-renders with fresh lists, as the dashboard does; the template keeps only transient state (the current step, field drafts, the live margin).
- `app/demo/onboarding/page.tsx` mounts the template over `lib/demo/demo-onboarding.ts`: plain arrays in `useState`, ids `demo-…`, every operation resolving on the next tick, nothing on the network; reload discards everything. It is not linked from anywhere, carries `noindex`, and accepts the test seams `?paso=N` (open on step N), `?e2eSeed=1` (Vivienda and Comida, Sueldo 2 000 on day 1, Alquiler 820 on day 1 in Vivienda, so the budget and savings steps can be tested directly), `?pais=AR&formato=abreviado` (profile overrides) and `?e2eInvite=0` (the closing screen without the code field). A one-line notice at the top says it is a sandbox and nothing is saved (`onboarding.sandbox`).
- Why a second mount instead of specs against the real route: every UI spec of the project runs without a database, by the same device (`/demo`). The real route needs an account and a code by mail.
- Why `Pick<…>` of the existing contracts and not new ones: the writes *are* the dashboard's; a parallel contract would be a second place for the same rules.

**D3. `ProfileMutations`, the one new contract.** `lib/data/profile.ts`:
```
type ProfileBasics = { name: string; country: string; currency: string; timezone: string; cycleDay: number; amountFormat: 'completo' | 'abreviado' }
type ProfileMutations = {
  updateBasics(basics: ProfileBasics): Promise<void>          // rejects 'cycle-locked' (D6), 'invalid-country', 'invalid-currency', 'invalid-timezone'
  setSavingsTarget(amount: number | null): Promise<void>
  requestWhatsApp(phone: string, inviteCode: string | null): Promise<void>  // rejects 'phone-taken', 'invalid-phone'
  setStep(step: number): Promise<void>
  complete(): Promise<void>                                     // onboarding_completo = true
}
```
`lib/data/supabase/profile.ts` updates the user's own `usuarios` row (RLS `usuarios_update_propio`), with `.select('id')` + `expectRows` so a foreign id or a missing row rejects. Validation runs in the server action, not in the browser: `name` trimmed and 1–80 characters; `country` in the table of D4; `currency` an ISO 4217 code the table knows (`^[A-Z]{3}$` is also the DB check); `timezone` one of the country's zones; `cycleDay` 1–28 (the DB check); `amountFormat` `'abreviado'` accepted only when `country === 'AR'`, otherwise stored as `'completo'`; `phone` normalised to E.164 (D11); the DB's unique on `telefono` surfaces as `phone-taken`. `/dashboard` receives the same contract (`DashboardActions.profile`) for the account sheet (D16); `/demo` supplies none.

**D4. The country table and what it derives.** `lib/data/countries.ts` is a constant list, no data access: `{ code, currency, callingCode, timezones: string[] }` for Argentina (`ARS`, `+54`, the twelve `America/Argentina/*` zones, Buenos Aires first), Uruguay, Chile, Paraguay, Bolivia, Peru, Ecuador, Colombia, Venezuela, Mexico, Guatemala, Costa Rica, Panama, Dominican Republic, Spain (`Europe/Madrid`, `Atlantic/Canary`), Portugal, Ireland, United Kingdom, France, Germany, Italy, Netherlands, Belgium, Switzerland, United States (six zones), Canada, Brazil, Australia. Names come from `Intl.DisplayNames(locale, { type: 'region' })`, so no catalog keys; the select is sorted by the localised name. Rules:
- **Default country** on first display: the country whose `timezones` include the stored timezone (the browser's, from `0025`); otherwise none selected and "Continuar" disabled until one is chosen.
- **Country → currency**: choosing a country sets the currency select to the country's currency; the currency select stays editable (the distinct currencies of the table plus `EUR` and `USD`), because people live in one country and spend in another (`ARCHITECTURE.md` §4).
- **Country → timezone**: the stored timezone is kept when it belongs to the chosen country; otherwise the country's first zone is stored. The screen shows the result as one derived line under the select ("Pesos argentinos · hora de Buenos Aires", the zone's city from the IANA name), not as a field.
- **Only `ARS` is new to the catalog of currencies the app knows** (`moneda_default` has no enum; the check is `^[A-Z]{3}$`). A country not in the table cannot be chosen; adding one is one line. Unit test: every `currency` formats with `Intl`, every zone is in `Intl.supportedValuesOf('timeZone')`, no duplicate codes.

**D5. ISO country code in `usuarios.pais`.** Stored as the two-letter code (`'AR'`, `'IE'`), which is what Brian's row already holds. No new constraint on the column (the server validates against the table).

**D6. The cycle day is editable only while nothing is keyed to the cycle.** `updateBasics` compares the new `cycleDay` with the stored one; a change is accepted only when the account has no category, no definition, no budget row and no transaction (`hasData` false; one `exists` query over the four tables in the action), and rejects `cycle-locked` otherwise. The template disables the day field when `hasData` is true and shows the hint `onboarding.ciclo.bloqueado` ("Se fija con la primera categoría"). In step 2 of a fresh account `hasData` is false, so a change writes `dia_inicio_ciclo` and nothing else: there is no `presupuestos.periodo`, no `categorias.desde_ciclo`, no `ciclo_mes` to re-key, and `rango_ciclo` derives every later cycle from the new day. Going back to step 2 after step 3 shows the field locked. The "Cuenta" sheet (D16) shows the day as a read-only line. The debt entry "`presupuestos.periodo` si cambia `dia_inicio_ciclo`" stays open for the day a settings control is wanted.

**D7. The seven steps and what each one stores.** One primary action per step ("Empezar" on 1, "Continuar" on 2–6, "Vincular" / "Seguir sin WhatsApp" on 7), "Volver" from step 2 on. Steps 3–6 can be continued empty: the product should not force a list on anyone, and the dashboard lets them add later.

| Step | Screen | Stores (through) |
| --- | --- | --- |
| 1 | Welcome: logo, "Hola. Vamos a armar tu mes." and three lines naming what comes (categorías, fijos, presupuestos → margen libre). No name (it is the e-mail's local part), no congratulation. | `setStep(2)` |
| 2 | Basics: name, country, currency, the format toggle (Argentina only), cycle day. | `updateBasics` on "Continuar", then `setStep(3)` |
| 3 | Categories: suggestion chips + composer + list. | `categories.create / update / delete` per action |
| 4 | Income and fixed expenses: two lists with a composer each. | `recurring.create / update / stop / delete` per action; `materializeCurrentCycle()` on "Continuar", then `setStep(5)` |
| 5 | Budgets with the live free margin. | `categories.update(id, { name, color, budget }, { cycle: start, scope: null })` on each field commit |
| 6 | Savings target. | `setSavingsTarget` on "Continuar" (null when empty) |
| 7 | WhatsApp: number, code (while required), "Vincular" or "Seguir sin WhatsApp". | `requestWhatsApp` (only "Vincular"), `materializeCurrentCycle()`, `complete()`, then `router.replace('/dashboard')` |

The name field in step 2 is prefilled with the stored name only when it looks like a name (letters and spaces, no digit, dot, plus or underscore); otherwise it is empty with the handle as placeholder, so "brianrebadj+alta1" never becomes a name by inertia.

**D8. Categories (step 3): chips, a composer, no sheet.** Eight suggestion chips from the catalog (`onboarding.sugerencias`: Comida, Vivienda, Transporte, Ocio, Salud, Suscripciones, Compras, Otros); tapping one creates it and the chip leaves the row; a composer (name field + "Añadir") creates a typed one. Colour: the first of `CATEGORY_COLORS` no category uses (the rule the sheet and the bot already follow). Each category is created with `create({ name, color, budget: null }, cycle.start, 'onward')`, so `desde_ciclo` is the cycle in progress, as the dashboard would. A row shows the dot and the name; tapping the name edits it inline (`update` on blur, `DUPLICATE_CATEGORY_NAME` shown as the sheet shows it); tapping the dot opens `ColorSwatchPicker` under the row (`update`); `swipe-to-delete` with its undo calls `delete(id, null, { cycle: start, scope: 'onward' })` — a category of a fresh account holds no rows, so no receiving category is needed; when it already holds a definition (the person came back from step 4), the function rejects and the toast says to remove its fixed expenses first (`onboarding.categorias.tieneFijos`). Why no `category-sheet` here: it asks "Vale para: solo este mes / desde este mes", a question with no meaning on a first setup, and a sheet per category is slow for a list of eight. The sheet's rules (trim, duplicate check, colour from the palette) are the contract's, so they hold.

**D9. Income and fixed expenses (step 4), and the pending charges.** Two lists on one screen: "Lo que cobrás" (income definitions) and "Lo que pagás todos los meses" (expense definitions). Each has a composer: name, amount (`AmountField`), day of the month (`IntegerField`, 1–31) and, for expenses, a category chip row (the categories of step 3; the composer is disabled with a line when there are none). "Añadir" calls `recurring.create({ tipo: 'ingreso' } | { tipo: 'gasto', categoryId }, { name, expectedAmount, day, reminder: { active: false, daysBefore: 0 }, repetitions: null })`. A row shows name, amount and "día N" (and the category dot for expenses); tapping it opens `recurring-sheet` (the definition sheet, reused as is: name, amount, day, reminder, "Dejar de repetir", delete), with `currentAmount` = the expected amount. No instalment plans and no reminder in the composer (out of scope; the sheet exposes the reminder).

The charges of the cycle in progress: on "Continuar" of step 4 and again in `finish()` (step 7), `materializeCurrentCycle()` reads the user's definitions, computes the cycle's charges with `proyectarCiclo({ start, cyclesAfterGenerated: n, definitions, budgetRows: [], savingsTarget: null })` — `n` = cycles between the last generated cycle and the one in progress, as `futureCycles` computes it (1 with a null marker, 0 when the marker is the cycle in progress) — and calls the new function `insertar_cargos_pendientes(p_usuario_id, p_periodo, p_cargos)` (`0029`): `security invoker`, callable by `authenticated`, `p_periodo` must be the cycle in progress or later (`>= periodo_presupuesto(p_usuario_id, null)`), every `fecha` inside the cycle (`fin_de_ciclo`), inserts one `pendiente` row per active definition of the user with the same columns `generar_ciclo` writes (`moneda` = `moneda_default`, `es_fijo`, `ciclo_mes`, `fecha` at local noon), `on conflict (movimiento_recurrente_id, ciclo_mes) do nothing`, and calls `sumar_repeticion` for each row it inserted — which counts only when the cycle was already generated, so a cycle the cron has not generated yet is counted by `generar_ciclo` when it does, once. It never touches `ciclo_generado_hasta`. Idempotent: the second call inserts nothing.
- Why not `editar_cargo_en_ciclo` per definition: in the cycle in progress it inserts the row **confirmed** (its caller is the entry sheet, where the row is real). An onboarding rent dated the 28th would show as taken on the 5th, and the bot's "alquiler 820" would answer "ya cargado".
- Why not wait for the cron: the person would finish the onboarding, open the dashboard and see no charge and a margin different from step 5's until 05:00 UTC the next day. If the cron already ran for the cycle (registered last night, onboarded today), `generar_ciclo` returns 0 and the charges never appear this cycle.
- Why not `generar_ciclo` through the admin client in the action: it is revoked from users on purpose (the cron owns the marker), it is a no-op once the marker is set, and the dashboard rule is "no service-role key in the web's path" (`dashboard-data`). The new function has exactly the write the onboarding needs and nothing of the cron's bookkeeping.
- Deleting a definition in step 4 after materialisation: `RecurringMutations.delete` soft-deletes its charges and removes it — the same as the dashboard. Editing the amount from the sheet: `update` rewrites this cycle's pending charge, as the dashboard.

**D10. Budgets (step 5): the live free margin.** The screen is the moment that explains the model, so it is built around one number. Layout, top to bottom: the step title (`font-display text-headline-lg`), the hero — the label "Margen libre" (`text-body-lg text-muted-foreground`) and the amount in `--brand-ink` with the dashboard's `hero-value` treatment (`text-display-mobile`, `sm:text-display`, glow in dark only, `hero-card--negative` when below zero) — a one-line explanation under it (`onboarding.presupuestos.explicacion`: "Lo que te queda después de tus fijos y tus sobres."), the **envelope bar** (D14), and the list of categories, each row with the dot, the name, a muted caption with the category's fixed total when it has one ("Fijos: 820 €") and an `AmountField` for the budget, empty meaning no budget. The margin is computed in the browser on every keystroke with `getFreeMargin({ income: Σ income definitions' expected amounts, savings: 0, categories: categories.map(c => ({ budget: parsed(field) ?? null, spent: Σ expense definitions in c })) })` — the same function and the same inputs the dashboard will have, because the pending rows of step 4 are those definitions at their expected amounts and the cycle's savings movements are zero. The field writes on commit (blur or Enter) through `categories.update(id, { name, color, budget }, { cycle: start, scope: null })`, which `actualizar_categoria` turns into the budget row of the cycle in progress (`periodo` = its first day); an invalid value (not > 0 or more than two decimals) shows the sheet's message and writes nothing; a failed write restores the previous value and shows the sheet's "No se pudo guardar". `budget: null` on an emptied field writes the "no budget" marker, as the sheet does. The envelope bar: one track the width of the column; from the left, one segment per category with a budget or fixed charges, sized `max(budget, fixed) / income`, in the category's colour, then the remainder in `--brand-ink` (the margin); when the reserved sum exceeds the income the track fills and the margin segment disappears while the number turns negative. With zero income the bar is not shown and the hero reads the negative of the reserved sum, with a line "Agregá tus ingresos para ver el margen" linking back to step 4. Reduced motion: the number changes in place (D14).

**D11. Savings target (step 6) and the closing screen (step 7).** Step 6 keeps the hero of step 5 on screen (it does not re-enter) and shows one `AmountField` ("Meta de ahorro por mes", optional). While the field holds a value, a muted line under the hero reads "Con esta meta te quedan {monto} por mes" = margin − target: it previews what a projected cycle shows (`proyectarCiclo` reserves the target), without changing the hero, because in the cycle in progress the dashboard subtracts the movements actually made, not the target. "Continuar" writes `setSavingsTarget(value | null)`.

Step 7, the closing screen: a short line explaining that the bot is optional and, today, by invitation; a phone field (`type="tel"`, placeholder with the country's calling code, e.g. `+54 9 11 …`); the invitation code field only when `inviteRequired` (the page reads `isInviteRequired(process.env.WHATSAPP_REQUIRE_INVITE)` on the server and passes it down; the sandbox takes `?e2eInvite=0`); the primary "Vincular" (enabled when the phone parses and, if required, the code is non-empty) and the secondary "Seguir sin WhatsApp". "Vincular" calls `requestWhatsApp(phone, code)`: the phone is normalised in the action — digits only, a leading `00` becomes `+`, a number without `+` gets the account's country calling code — and must match `^\+[1-9]\d{6,14}$` (the `usuarios.telefono` check); it is stored in `usuarios.telefono` (the contact phone the account menu shows), the code trimmed and uppercased in `usuarios.codigo_invitacion`, and `usuarios.whatsapp_solicitado_en = now()`. A unique violation on `telefono` surfaces as "Ese número ya está en otra cuenta" and keeps the screen. Then `finish()` runs `materializeCurrentCycle()` and `complete()`, and the page navigates to `/dashboard`. The stub: `lib/whatsapp/link-request.ts` exports `requestChannelLink(usuarioId): Promise<{ sent: false; reason: 'template-pending' }>`, documented in its header (what block 10 replaces it with: the Meta template, the `invitaciones` check, the channel row), called by the action after the write and ignored. The success copy is honest: "Guardamos tu número. Cuando el bot esté listo para vos, te llega un mensaje de Mango." No channel row is created: `canales` stays the bot's (block 10 writes it when the link is confirmed from WhatsApp).

**D12. `ARS` and the amount format.** Three pieces:
- **Locale and symbol.** `currencyFormatOptions` gains `currencyDisplay: 'narrowSymbol'` (`€`, `$`, `£` unchanged for the currencies in use; `ARS` and `USD` stop showing a code). A new `amountLocale(locale, currency)` in `lib/data/amount-format.ts` returns `'es-AR'` for `es` + `ARS` and the locale itself otherwise, so Spanish shows `$ 350.000` (symbol first, space, as in Argentina) and English `$350,000`; euros keep `350 €` / `€350`. Every formatter (`Money`, `AnimatedAmount`, `AmountField`'s symbol, the sheets' prefilled values, `formatBotAmount`) goes through this module.
- **The preference.** `usuarios.formato_montos text not null default 'completo' check in ('completo', 'abreviado')` (`0029`). The effective format is `pais === 'AR' ? formato_montos : 'completo'`, computed in one place (`effectiveAmountFormat(usuario)`) so the toggle "does not exist and changes nothing" for any other country even if the column holds `abreviado` from an earlier choice. It travels as `DashboardData.user.amountFormat` and `OnboardingData.profile.amountFormat`; the templates wrap their tree in `AmountFormatProvider` (`components/atoms/amount-format.tsx`, a React context defaulting to `'completo'`, so `/demo` and every existing mount need no change); `Money`, `AnimatedAmount`, `AmountField` read `useAmountFormat()`. The bot's `BotFormat` gains `amountFormat`, set in `processMessage` from the same helper, and `formatBotAmount(locale, currency, amount, amountFormat)` formats with the same function.
- **The abbreviated rules** (`formatAmount(amount, { locale, currency, amountFormat })`, pure, in `lib/data/amount-format.ts`, relative imports so Node loads it):
  1. `completo`, and `abreviado` below 1 000 in absolute value: `Intl.NumberFormat(amountLocale(locale, currency), { ...currencyFormatOptions, currency })` — today's output, cents when the amount has them (`$ 62,40`).
  2. `abreviado`, 1 000 ≤ |amount| < 999 950: figure = |amount| / 1 000, rounded half away from zero to one decimal (`Math.round(|amount| / 100) / 10`), the decimal dropped when zero, suffix `k` glued to the figure: `1.500 → 1,5k`, `12.345 → 12,3k`, `350.000 → 350k`, `1.000 → 1k`.
  3. `abreviado`, |amount| ≥ 999 950: figure = |amount| / 1 000 000 with the same rounding, suffix `M`: `1.500.000 → 1,5M`, `999.950 → 1M`, `12.345.678 → 12,3M`; from a thousand million the figure keeps its grouping: `2.500.000.000 → 2.500M`. Nothing above `M`.
  4. No cents and never more than one decimal in an abbreviated figure. The decimal and group separators are the locale's (`,` and `.` in `es`, the reverse in `en`), produced by `Intl.NumberFormat(amountLocale(…), { maximumFractionDigits: 1 })`.
  5. Sign and symbol come from `formatToParts` of the full form in the same locale: the abbreviated figure replaces the `integer`, `group`, `decimal` and `fraction` parts and every other part stays in place. So `es`: `$ 350k`, `-$ 1,5M`; `en`: `$350k`, `-$1.5M`; a euro account that somehow held `abreviado` would read `1,5M €`. The minus is the one `Intl` emits.
  6. Inputs never abbreviate: `AmountField` keeps the full number and shows only the symbol; the sheets prefill full values (`formatBudgetForEdit` unchanged).
  7. Compact chart labels (`compactFormatOptions`, "1,7 mil") are unchanged: they are a chart convention, not the preference.
  Unit tests (`lib/data/amount-format.test.mjs`) cover the table above in both locales, the boundaries 999,99 / 1 000 / 999 950 / 1 000 000 / 1 000 000 000, negatives, `completo` for `ARS`, and the es-AR symbol order; `lib/bot/format.test.mjs` gains an `ARS` + `abreviado` confirmation ("Anotado ✅ Super · $ 15k en Comida. Llevás $ 48k de $ 300k este mes 🟢").
- **The counter.** `AnimatedAmount` keeps `CountUp` and passes `format: value => formatAmountFigure(value, …)` so the digits roll in the abbreviated unit when the format is `abreviado` (`0 → 350k` reads `12,3k … 349,8k … 350k`), and the symbol beside it comes from the same parts.

## Risks / Trade-offs

- [`insertar_cargos_pendientes` is a second writer of charges] → it inserts only pending rows of the user's own active definitions into the cycle in progress or later, `on conflict do nothing`, and counts through `sumar_repeticion`'s guard; the cron skips existing rows and counts each definition with a row once. The manual pass runs the cron route after an onboarding (marker null) and again after a cron-first case (marker set) and checks `repeticiones_insertadas` and row counts.
- [The live margin and the dashboard disagree] → same function, same inputs (D10); the manual pass compares the two numbers. If the cron generated the cycle *between* step 4 and step 7, nothing changes: the function is idempotent.
- [A person edits the cycle day after categories exist by going back] → `cycle-locked` on the server and a disabled field on the client (D6).
- [`narrowSymbol` changes `USD` to `$`] → no account uses `USD` today; the demo and Brian are `EUR`.
- [`es-AR` only for `ARS`] → other Latin American currencies would still read symbol-after in `es` (`350.000 $` for `MXN`); none is in use; extending the map is one line and is noted as debt.
- [The theme default differs between the onboarding (system) and `/demo` for a first-time browser (dark)] → the onboarding stores `system`, so after it the whole app follows the OS for that browser; the landing/login remain forced dark; `/demo` is a public page with its own look. Named in the `theming` delta.
- [`usuarios_update_propio` has no column list] → pre-existing: a user could update `vip` or `cargas_confirmadas` through the API with their own JWT. This change adds columns to that surface (`onboarding_completo`, `formato_montos`) that are the user's to set anyway. A column-level policy is noted as debt, not done here.
- [The "Cuenta" sheet makes mixed currencies reachable] → the line under Moneda says the sums do not convert; the debt entry stays.
- [Chips create categories on tap, so a mis-tap creates one] → swipe to delete with undo is two gestures away; the create is the same cheap write as the sheet's.
- [`/demo/onboarding` is public] → it holds no data and writes nothing; `noindex`; the same exposure as `/demo`.
- [The welcome's bounce curves on a 2026 consumer bar] → they are the dashboard header's own entrance, so the product's personality is consistent (`AUDIT.md` §7); reduced motion removes them.
- [Prefilling the name from the e-mail's local part] → only when it looks like a name (D7); otherwise empty with the handle as placeholder.
